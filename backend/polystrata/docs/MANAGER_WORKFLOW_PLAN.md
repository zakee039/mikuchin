# PolyStrata 自适应 Prefill 与 Workflow Prefix Cache 研究计划

> **状态：设计讨论稿（尚未实施缓存新功能）**
> 修订：2026-11-01
> 适用基线：`zakee039/PolyStrata` 的 `polystrata` 分支；Manager v0.1.7，生产配置为 128K MeroMero
> 目的：梳理研究选项、系统边界和验收方法。**本文件不是开发授权**；未确定方案前，不修改服务端、C++ 引擎、Manager、模型、配置或既有 KV 数据。

## 0. 一句话目标与新的问题定义

过去的提议是 **Workflow Registry + 手动预热 Prefix KV**：让 Miku Harness 提前注册稳定的 System Prompt，服务端缓存并复用它的 KV。

讨论 `Prefill-as-a-Service（PrfaaS）` 后，进一步考虑：

> **让 PolyStrata 在普通 API 请求和显式注册工作流中自动发现稳定、可重用且“值得保存”的前缀；根据现有 RAM 缓存、磁盘恢复和重新 Prefill 的实际成本，决定是否创建、保存、恢复或丢弃缓存。**

这不是把 Prefill 放到另一台服务器上，而是研究**单机、资源受限、模型可卸载的持久化 KV 缓存调度**。是否引入真正的独立 Prefill 工作进程/远程服务，暂不决定。

研究名称（工作代号）：**Adaptive Prefill Cache Service（APCS）**；`Workflow Prefix Cache` 是其中一种高优先级应用场景，而非整个系统的唯一入口。

## 1. 文献启发与正确的差异定位

### 1.1 PrfaaS 做了什么

参考：[Prefill-as-a-Service: KVCache of Next-Generation Models Could Go Cross-Datacenter](https://arxiv.org/abs/2604.15039)，Ruoyu Qin 等，2026-04。

- 论文关注**跨数据中心 Prefill–Decode 分离**：对适合的长上下文请求，选择性地使用独立的 Prefill 计算资源，再将 KV Cache 传给 Decode 侧。
- 其核心约束包括未缓存的前缀长度、KV 传输开销、带宽波动、请求放置、队列和异构算力。
- **不能**把论文的跨数据中心调度机制、吞吐提升比例当成 PolyStrata 已实现功能，或直接套用到单台 RTX 3070 Ti 上。

可借鉴的系统原则：**不要“一律缓存”“一律卸载后恢复”或“一律外包 Prefill”，而应比较不同执行路径的真实净收益。**

### 1.2 PolyStrata 与其他前缀缓存系统的关系

- Strata 上游已有**相同 Token 前缀复用、会话 Checkpoint、根前缀 Checkpoint、RAM Parking/多会话缓存**。它并不需要每次从 Token 0 完整 Prefill。
- 当前 PolyStrata 定制版又有**会话级磁盘 SAVE/RESTORE、会话 SQLite、模型自动空闲卸载、手动停止模型**；会话磁盘 KV 通常保存的是会话检查点，**不能推论它支持任意固定前缀边界的独立持久化**。
- vLLM Automatic Prefix Caching、LMCache 等已有哈希/分块/多层 KV 管理思路；研究前应做功能和代价对照，避免把已有机制包装成创新。

参考资料：
- [Strata 原生实现文档](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md)
- [Strata 并行与缓存说明](https://github.com/Niko1221/Strata/blob/main/docs/BATCHING.md)
- 本地 `src/poly/conversations.hpp`、`src/poly/session_disk.hpp`、`docs/SESSION_V1.md`

**研究差异候选**：跨卸载周期保留高价值前缀 + 自动准入与回收 + 三路径成本感知调度 + Agent 工作流上下文。

## 3. 两种使用入口、一个决策内核

### A. 显式 Workflow（确定性）

Miku Harness 等可信客户端注册固定前缀：System Prompt、工具定义、模型和模板配置、版本。

- 可以显式请求预热、更新、Pin 或删除缓存。
- 客户端是定义权威来源；内容变化需要重新注册和校验。
- 注册是元数据操作，**不等于立刻创建 KV**；预热、持久化仍受资源与安全约束。
- 显式 Pin 可以提高保留优先级，但不得突破配额或覆盖普通会话数据。

### B. 隐式候选发现（自动化）

普通 OpenAI 兼容接口无需修改请求：服务端观察**完全相同、被多次使用的渲染后 Token 前缀**。

- 观察到重复前缀时，先记录哈希、长度、使用频率、收益估计；**观察期不保存新 KV**。
- 只有符合准入策略的候选，才考虑在安全的精确边界创建或复用 checkpoint。
- 首期不跨越不同模型、模板、权限域、图像和不同 Token ID 强行共享。
- 不缓存仅仅“语义相似”的文本；动态日期、工具结果、记忆检索、实时截图必须视为可变内容。

**共同内核：**准确性校验 → RAM 缓存查询 → SSD 缓存查询 → 成本比较 → 正常 Prefill / RAM 恢复 / 磁盘恢复 → 记录决策结果。

### 请求路径（概念）

`请求 → 模板/工具渲染 → Token 与兼容指纹 → 精确前缀匹配`

`　　├─ RAM 中已有更长可用会话：优先就地复用`

`　　├─ 独立的磁盘前缀缓存：仅净收益为正且恢复无害时读取`

`　　└─ 不命中/恢复不划算：照常 Prefill，候选由观察器统计`

所有新增机制应支持 **Off / Observe / Auto** 逐级启用；默认不改变原生推理路径。

## 4. “值得保存”与“值得恢复”必须分开

### 4.1 保存准入（Admission）

设计候选的净收益分数（**研究公式，不是已验证的算法**）：

`V_save(p) = E[N_future(p)] × [T_cold(p) − T_restore(p) − T_pollution(p)] − T_save(p) − λ × S(p)`

含义：
- `E[N_future]`：缓存寿命内预计重复次数，不能仅按历史次数无条件外推。
- `T_cold`：当前设备上重新 Prefill 该有效前缀的耗时。
- `T_restore`：读取 SSD、校验、主机/设备传输与恢复状态的总耗时。
- `T_pollution`：磁盘 RESTORE 清除或挤占其他 RAM Parking / Checkpoint 造成的机会成本。
- `T_save` 和 `S`：保存耗时、文件大小；`λ` 为容量预算的影子价格。

可能纳入的信号：前缀长度、过去窗口的使用次数、重复间隔、实际 Prefill 速率、恢复耗时、模型启动周期、剩余 SSD/RAM 预算、失效频率、TTL。

**准入原则**：冷启动时观察，不凭“超过 4096 Token 就保存”一条硬规则决策；建立保守阈值、最小样本、冷却时间和滞回，避免频繁写盘/反复淘汰。无足够数据时不作高置信度收益宣称。

### 4.2 每次调用的恢复选择（Placement）

比较三个候选动作：

| 执行动作 | 主要成本 | 必要条件 |
| --- | --- | --- |
| RAM 继续复用 | 当前可继续位置、Checkpoint 切换成本 | Token / 模型 / 状态完全兼容 |
| SSD 恢复独立前缀 | 文件校验、磁盘读取、状态上传、RAM 失效代价 | 内容兼容、完整、成本优于其他路径 |
| 重新 Prefill | 实际未命中 Token 数与当前设备吞吐 | 总是要有安全回退 |

在现有 `Conversations::disk_adopt` 路径，**RESTORE 会清空其他驻留 Slot/Checkpoint**。这个副作用应算入成本；当前不应把“磁盘命中”自动等同于“应该恢复”。

预热（warm）占用同一推理引擎，不能打断前台请求、破坏 FIFO 或触发手动停止模型的自动加载。优先空闲时低优先级运行；手动 `paused` 状态下禁止任何自动预热。

## 5. 准确性与快照生命周期

- **两重兼容校验**：模型权重/Tokenizer/模板/引擎构建/KV 格式/位置编码等兼容指纹 + 完整渲染后的 Token ID 前缀哈希与长度。
- **边界正确性**：快照应在精确前缀末尾、首个动态 Token 之前创建；保存该位置的全部必要 recurrent state 和 attention rows。现有 `disk_point()` 取会话 Checkpoint 的方式不应未经验证直接复用。
- **不可变与失效**：不可变缓存内容由哈希命名；定义更改产生新版本，旧文件经引用检查和预算策略清理。文件写入原子化，校验失败安全回退，不删除聊天或普通会话 KV。
- **隔离**：Workflow 缓存采用独立目录 `workflow-cache/` 与单独容量配额；不参加普通会话 5 份 FIFO，不可覆盖 `kv-cache/`、`chat-history/`。
- **恢复副作用**：先做 RESTORE 改造可行性实验，验证是否能不清空其他会话；若不能，第一版调度器必须识别代价并允许拒绝恢复。
- **多模态**：V1 仅文本固定前缀；图像及视觉投影相关内容不宣称可持久复用，需另行验证。
- **结果校验**：至少检查恢复前后 Token 一致性、生成确定性边界、异常回退、模型切换与长上下文稳定性。

## 6. API 草案（未实现、不代表最终协议）

### 6.1 普通客户端零改造

`POST /v1/chat/completions`、Responses 等现有接口维持兼容；缓存策略默认由服务端决定，不要求每个客户端注册 Workflow。

### 6.2 高级客户端可选扩展

`strata_cache` 是拟议字段，具体命名待定：

`{"mode":"auto","workflow_id":"miku-memory"}`

- `off`：不启用新增持久前缀缓存；保留既有会话级行为（定义需统一）。
- `observe`：只采样候选，不构建或恢复新增缓存。
- `auto`：允许服务端自主准入与恢复。
- **Pin 不是普通推理请求的无权限标志**；固定资源保留应由单独的受认证管理接口完成。

### 6.3 独立管理接口草案

| 接口 | 含义 |
| --- | --- |
| `PUT /v1/strata/workflows/{id}` | 注册/更新版本化 Workflow 定义 |
| `GET /v1/strata/workflows` | 查询定义、缓存状态、关联模型 |
| `POST /v1/strata/workflows/{id}/warm` | 请求低优先级预热任务 |
| `GET /v1/strata/cache/stats` | 查询缓存与 Prefill 收益统计 |
| `GET /v1/strata/cache/entries` | 查询候选、来源、大小、命中及决策原因 |
| `PATCH /v1/strata/cache/entries/{id}` | 配额允许时 Pin、调整优先级或禁用 |
| `DELETE /v1/strata/cache/entries/{id}` | 删除**缓存**，不删除工作流或聊天 |
| `DELETE /v1/strata/workflows/{id}` | 删除注册定义（与删除缓存区别明确） |

后续可为响应提供 `cached_tokens`、`computed_tokens`、`cache_source`、`restore_ms`、`estimated_saved_ms`、`cache_decision`、`rejection_reason`。值必须来源于真实计时、计数或明确标注的模型预测；无有效测量返回 `null`，不能填示例数字。

### 6.4 远程访问边界

当前 Manager 只有单一 API Key；它不足以证明不同调用方之间有独立租户身份。**不能把客户端随意传入的 scope、workflow_id 或 cache_salt 当作授权依据**。

- 首版只在单用户可信环境观察候选；默认不跨独立客户端共享可观测的私有缓存。
- 启用 LAN / Cloudflare Tunnel 前，管理接口和推理接口必须进行认证、访问控制、速率限制与权限隔离审查。
- 未来如需跨应用/租户共享，考虑单独 API Key/Client ID 与服务端授权绑定；不可凭请求字段自行声明自己属于某个租户。
- 统计默认只保留脱敏哈希、Token 数、时间与成本，不记录用户 Prompt 原文；缓存文件内容本身敏感，需要本机文件权限控制、删除策略和磁盘占用限制。

## 7. 分阶段研究路线（每阶段有停手条件）

### R0 基线复核与测量工具（只读）

- 固定当前分支、模型、128K 配置、Prompt Cache/RAM Parking 参数。
- 梳理 `resume`、`before/inside`、`disk_point`、`disk_adopt`、`SessionV1` 实际调用链。
- 用独立合成请求测 Prefill/token、Checkpoint 创建、保存、读取、校验、恢复、RAM Slot 被清空的代价。
- 产出：功能对照表、真实耗时/容量数据、需要扩展的 C++ 精确边界。
- **停止条件**：若已有缓存足够有效，新增持久化收益可能不成立，暂不继续。

### R1 Shadow Scheduler（先观察，绝不改变推理输出）

- 服务端以不保存原文的方式识别重复的**已渲染 Token** 前缀。
- 记录候选命中次数、有效长度、出现间隔、成本估计与被拒绝原因。
- 离线回放测试不同准入算法；不自动写工作流 KV。
- **停止条件**：真实负载缺乏稳定可重复前缀，或观察器开销过高。

### R2 精确前缀 KV 原语与独立缓存目录

- 经设计评审后再考虑 C++ Prefill-only / exact-prefix-checkpoint。
- 先做手动注册、预热、恢复，不做自动策略，验证 Token 级正确性与损失风险。
- 同时保证会话快照和普通历史数据不受干扰。
- **停止条件**：恢复净收益不明显，或破坏现有会话缓存的风险不可控。

### R3 成本感知自动准入 / 调度

- 对照固定阈值、LRU、复用次数策略与预测收益策略；分别测试存入 SSD 和从 SSD 恢复的决策。
- 增加磁盘配额、TTL、失效与淘汰，避免后台预热干扰前台请求。
- **停止条件**：预测策略无法稳定优于简单基线，优先保留简单可解释策略。

### R4 API、Manager 与 Miku Harness 集成

- 仅在 R2/R3 正确后增加稳定的注册和查询 API、Manager 工作流页。
- Miku Harness 的稳定 System Prompt/工具定义通过 Workflow 注册；动态记忆与截图保持增量部分。
- 保留无需改造客户端的普通 OpenAI API 路径。

## 8. 实验设计与评价指标

**基础硬件**：Windows 10，i7-12700、RTX 3070 Ti 8GB、64GB DDR4-3600 RAM。实际测试模型、KV 精度、上下文、SSD 类型、构建哈希和运行配置必须逐项记录，不能混入笔记本 GPU 数据。

**对照实验**（先合成、后真实 Miku Harness 轨迹）：
1. 现有 Strata：RAM Checkpoint/会话复用，无新增持久前缀缓存。
2. 现有 PolyStrata：会话 SAVE/RESTORE，无新增 Workflow 缓存。
3. 仅显式 Workflow 预热 / Pin。
4. 自动阈值缓存与 LRU 淘汰。
5. 成本感知准入 + RAM/SSD/重新 Prefill 三路径调度。

**固定前缀长度**：1K、4K、16K、32K Token；观察不同重复概率、重用间隔、系统提示词变化和模型卸载周期。大于可用资源或真实上下文的实验要报告为不支持，不得默默降低规格。

**指标**：TTFT p50/p95、Prefill 新处理 Token 与速率、缓存恢复 p50/p95、端到端请求延迟、有效命中 Token 率、吞吐、CPU/GPU RAM、SSD 容量与写入量、恢复导致的 RAM Cache 淘汰、模型重载时间、错误/回退率。

**关键消融**：无自动发现、无成本模型、无磁盘持久化、无 RAM 优先、无淘汰成本、无 Workflow 显式提示。必须报告最差案例与负收益，而非只展示最佳结果。

**可靠性回归**：错模型/错 Tokenizer、损坏文件、异常退出、同时多请求、模型空闲卸载后恢复、手动 `paused` 不自动加载、单槽 FIFO、一批普通会话快照和多模态请求安全回退。

## 9. Manager UI 的最小原则

保持现有 4 个主要 Tab（总览 / API / 工作流 / 设置），在**工作流**页面新增尽量克制的信息视图：

- 概览：已注册工作流、已就绪缓存、自动发现候选、磁盘占用。
- 条目：Workflow/候选名称或短 ID、前缀 Token、状态、最近收益、缓存来源。
- 操作：注册、预热、Pin/取消、删除缓存；高级调度设置放二级弹窗，不增加大段说明文本。
- 区分“注册成功”“预热完成”“可命中”“实际命中”四种状态，不用一个绿色标签混淆。
- 不在 Manager 中实现 KV 二进制读写或另一套调度器。

## 10. 研究决策仍需讨论

这些属于未定设计，不应在开发前擅自固定：

- **产品范围**：仅优化可信的 Miku Harness 工作流，还是对所有 OpenAI API 请求默认开启候选发现？
- **默认模式**：Observe 默认是否长期保持？Auto 要求用户明确启用还是作为后续默认值？
- **存储与隐私**：工作流固定前缀能否被本地长期保存、加密与删除策略怎么定义？
- **缓存位置**：先做仅 SSD，还是允许独立的 RAM 共享前缀池？恢复是否能不清除原有 parked slots？
- **研究价值**：如果原生 Strata 的根 Checkpoint 已解决主要瓶颈，跨卸载持久化带来的净收益是否足够？
- **API 兼容性**：是否保留 `strata_workflow_id` 独立字段，还是统一放进 `strata_cache`？先用哪个客户端验证？
- **模型状态**：手动停止模型是否完全禁止预热（建议禁止），显式用户重载时是否允许恢复 Pin 缓存？
